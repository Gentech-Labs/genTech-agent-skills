# Pitfalls — part 2 of 3

Part of the `develop-and-verify` ledger. **Index, part list and the census rule: `pitfalls.md`.**
Items were **MOVED WHOLE** — never rewritten — so each carries its own provenance line inside its own text.

- **A repository-LOCAL `user.name` cannot travel, so per-seat attribution must not rest on it.** A clone with `git config user.name` set locally while the global is a different account shows **60 of 60 commits authored by one constant name** — a populated, non-erroring field whose answer carries **zero** attribution. Any conclusion of the form *"that was X's commit"* or *"X swept my file"* drawn from `--author` is unfounded there. **Attribution on a shared clone must come from the SUBJECT and the CONTENT**, and a convention that works only because everyone follows it is a habit, not a mechanism — **a rebuild must carry it as config, not as goodwill.**
- **The most authoritative ledger is the RECEIVER's own inventory — read it before inferring from exclusions.** An entire evening went into inferring a transfer set from ignore rules and byte walks; the client's own state database held the answer the whole time (**6,017 server records, 124.3 MB, zero music paths**) and it agreed with the inferred model — which is what turned the model from assumed into **verified**. **A configuration tells you what SHOULD move; the receiver's inventory tells you what DID.** When both exist they are not redundant: the first is a claim, the second is a measurement.
- **A self-reporting WINDOW is what makes a difference between two runs legible instead of mysterious.** Two readers measuring the same repository a few commits apart get `5,497` and `5,526` — with the window printed, that reads as a **clock**; without it, it reads as a **disagreement** and costs an hour of reconciliation. **Build the window into the tool's own output**, not into the note that explains it.
- **The unit of the check decides what the check can see — the blind spot is always in the UNIT, never in the arithmetic.** Four instances in one day, one property: a `*.log` glob that can never match the rotated `agent.log.1`; a ref-count that can never see an exhausted credential pool; a **file-path** case-collision scan that reports 1 while a directory-aware scan reports 2 (two DIRECTORY names differing only by case share no lowercased file path); and a tracked-only scan that cannot see the ignored third casing of the same word. **When a check reports a count, ask what its unit is before trusting it** — and **prove the negative control too**: a tool that fires but cannot CLEAR is as unusable as one that cannot fire, so confirm the exit code in BOTH directions.
- **Count the FILE after a scripted append, never the string the script just built.** Twice in one night a script that appended two lessons to one file reused a variable name between the two additions, so the second silently clobbered the first before the write — and the script's own closing line (`pitfalls now: 94`) was computed from the string it HAD BUILT, so it cheerfully reported success for content that never reached disk. **A self-reported count is a claim about the author's intent; a count read back FROM THE FILE is evidence.** Re-open and grep for a distinctive phrase from each addition, or the loss is invisible — and it lands in the one artifact the whole fleet reads.
- **An acquittal is only as good as the UNIT it was computed in — class filters drop FILES, they do not drop FOLDERS.** A sync client was said to carry nothing from a set of code checkouts. Measured at the client's own log: **746 `Uploading <junk path>` lines, 0 `Upload complete` for junk FILES, and 1 `Push: .../node_modules/content-type`** — **the contents did not upload and the STRUCTURE was pushed.** *"It carries nothing"* reads as **"no action needed"**, which retires an investigation that should stay open. **A ledger of file content CANNOT see a folder-exclusion failure, because what leaks is SHAPE.** When acquitting a category, state the unit you measured and check whether the thing you cleared can fail in a unit you did not measure.
- **A bare folder name only excludes a TOP-LEVEL folder; anything nested needs an enumerated path.** An exclusion list carried `node_modules` and `.venv` as bare names, which did nothing for `<stack>/node_modules` — so two entries were replaced by **53 enumerated paths**, and **the length of that list is the defect's fingerprint.** The rule is not *"names are wrong, paths are right"*: bare names still work for top-level folders. **Ask why a config would need to enumerate paths one at a time — that shape IS the bug.**
- **A correction applied to the copy a peer pointed at is not a correction — sweep every sibling copy in the same pass.** A stale status line (*"sync is not live yet, do not rely on it"*) was fixed in the one notice a peer quoted, while **THREE live copies and an `_archive` copy of a second notice still carried the same wrong sentence.** The peer's catch is what exposed the others, hours later. **A fleet notice is a fan-out: N copies at N paths, and `_archive` is a copy too.** Before closing a correction, **grep the whole inbox tree for the stale phrase and verify a marker in EVERY hit** — the defect is identical to a single-path fix that misses a seat's archived copy.
- **A correctly written, correctly ordered guard that control never REACHES is still inert — assert the SPECIFIC status, not a set, and drive the guard's own condition through the real entry point.** A named safety assertion was repaired (declared→validated→used, in order, and a test asserting that ORDER). It still could not fire: **two of its three conditions were unreachable by construction** (the refspec was built from the same variable it was validated against, so `name != ref` could never hold), and the third sat **downstream of an earlier `return`** that every non-ancestor ref hits first. **The test passed because it accepted a SET of refusal statuses** — a different refusal satisfied it, and a green suite read exactly like an inert guard. **Order is necessary and not sufficient: an assertion that a call happens BEFORE the push proves nothing about reachability.** The only real proof is a case that triggers the guard's own condition through the CLI and asserts the exact status it returns.
- **A false alarm is worse than no check — it spends the trust the one real finding needs.** A first draft of a stub-pointer check raised **287 findings, almost all noise** (prose containing "deprecated", any backticked token), and the author reported it rather than shipping it. **287 means nobody reads number 288; the one true finding is buried by the false ones around it.** Tighten the predicate (size bound + phrase in a prefix + a single bare-token target) until the check is quiet on a clean subject, and **prove it both directions on a fixture** — target present → 0; target missing → flagged. **And print an EXAMINED count, not just a verdict:** a check that silently skips its subject reports exactly what a clean subject reports.
- **"Resolves for WHOM?" — a pointer check that resolves against the LOCAL DISK can be clean while the repository is not.** A redirect stub was cleared because `os.path.isdir(target)` returned true; the target directory was **gitignored with zero tracked files**, so in a fresh clone the same stub points at nothing. **Tracked stubs resolved against the untracked disk are two different universes.** Resolve against the TRACKED tree and report both (*"on disk 3/3 · in a clone 2/3"*) — the working tree and the repository are the two seats that read this vault, and they do not always see the same file.
- **A window-scoped observation stated as a whole-history fact makes the past look emptier than it is.** Sixteen of the last sixty commits were all authored by one name, so the author field was declared to carry **zero** attribution — over a history of 6,473 commits carrying **twenty** distinct author values, several of which DO attribute (`steward`, `Pixel`, `gizmo`, `gentech-treasury`). **The recent-window measurement was exact and the generalisation was not.** Before stating a property of "all commits", "all files" or "everywhere", **name the window the measurement actually covered** — otherwise the conclusion reads as stronger than the evidence in the direction that makes the past look uniform.

- **A guard list has to be audited at ENTRY level, not by its form — and the test is COUNT OF FILES EXCLUDED, not "does the path exist".** Three exclusion entries named top-level folders that no longer existed (0 files) and ten more named directories that existed and were **empty** (0 files) — **13 of 63 entries excluding nothing, and all thirteen have the exact form of the fifty that work.** Existence and emptiness are indistinguishable in the list, and both are indistinguishable in a class-level leak test, **because there is nothing to leak.** When you verify a guard set, count what each entry actually excludes; *"it is in the list"* is a claim about spelling, not about effect.
- **A config line can record a fix's HISTORY — duplication is a better defect fingerprint than length.** A name appeared bare once and as three paths, spanning the live tree and a retired copy of the same service: **a name and its own enumeration in one list is the scaffolding of a fix left visible, and the duplication recorded a fix applied across a MOVE.** Length, by contrast, measured the client's cache discovery (49 of 54 nested entries were auto-discovered caches that would be enumerated with or without the bug) — **a number that grows for reasons unrelated to the thing it is being used to prove is not a fingerprint.** Fingerprint the SHAPE the failure caused, not the size of the list it left behind.
- **A server that syncs notes tracks the SHAPE of every directory and the CONTENT of only the types it permits.** Measured across 3,288 content-bearing server rows: markdown plus the allowed image/pdf classes, and **exactly four code-class files — all of them client-written `.obsidian` config.** A folder entry with size zero is therefore the only record of a tree whose files never travelled, which is why folder entries can outnumber meaningful content and why *"the directory synced"* is not evidence that anything inside it did.

- **A cap that has never fired has never been measured — check for the LOG LINE, not the constant.** A per-file limit was cited across a dozen notes as a filter that "disqualifies" heavy files; the client's own constant was a different, much larger value, and the decisive evidence was that the source logs its own skip **with the value it compared against** and **no such line has ever been produced**, because no eligible file has ever been large enough. **Absence of a firing is not evidence of a threshold; it is evidence that the threshold is untested.** Before citing a limit as a mechanism, look for the refusal it has produced.
- **A projection is a division by its denominator, so an unread plan size makes every horizon an assumption.** A rate was measured exactly and then divided by a plan size that appears in no instrument (not in the client config, not in the status command). **"Fills in 7.9 months" is a measurement over an assumption; the rate is the measurement, the horizon is not.** State the form — *"at this rate, it fills SOME plan in 7–12 months"* — or find the instrument that reports the quota.
- **A policy you measured can change under you — re-read the config, not the conclusion.** `allowTypes` moved from a static list to including audio and video between two reads in the same hour, and audio/video files began landing on the server minutes later. **A statement true at read time ("it was never in the transfer set") becomes false silently, and the notes citing it do not move.** Record the mechanism as a policy with a read time, or it becomes a stale fact the whole fleet quotes.

- **Cite the artifact by PATH + DIGEST, not by path.** A tool was verified at source, quoted with a line count, and the path is a **stable shim** that now serves different content — so "I read the file" no longer implies "I read the file you last wrote." **A stable path is a silent supersession:** the name carries no clue that its target changed, and a shim keeps the announced name working precisely so nobody notices. Record a hash or digest when you verify; the line count is the receipt that let the author catch it.
- **Before reporting a false NEGATIVE, confirm your own pattern set is a superset of the one you are testing.** A pass reported 44 real events "missed" by another tool's patterns — every one of them was matched by a term the other tool already included and **my own pattern set omitted**. The finding was a property of my instrument, not theirs, and only a sample of the flagged lines revealed it. **A false positive wastes a reader's trust; a false negative about someone else's coverage misdirects their repair.**
- **A bare-token count inflates with the volume of NON-EVENT lines, not total volume.** Two seats with nearly the same log size (114k vs 130k lines) showed contamination ratios 1.8× and 4.5× apart, because the inflation is proportional to how much the harness logs that is **not** the event being counted — counters, telemetry, ids. **So the ratio is a statement about logging mix, and a seat that logs more non-events reads worse for no reason connected to what is being measured.** When one digit-string appears legitimately inside any numeric field, no correction factor is stable across seats.

- **A reachability claim computed from SOME of the refs is the `--all` bug wearing a preservation costume.** Two blobs were reported as existing "only in `vault/main`'s ancestry" and therefore lost to a retarget or rewrite — but reading the SERVER showed **seven refs reach them, six of them live remote branches**. A clone's `refs/remotes/*` are whatever that clone last fetched; **a stale remote-tracking ref set is not the server's ref set.** Before calling anything a one-way door, enumerate the refs on the REMOTE (`git ls-remote --heads`), not the ones in front of you — and then measure what is reachable **only** from the refs you are about to remove.
- **Publishing a list with no enumerated contents is how a residue survives as "accounted for".** A 24-object gap was explained as "extension-set width" — a correct SHAPE with no contents — and it stayed open across several turns until both parties printed their extension sets. **Then it closed in one comparison: the residue was scope, not extensions.** The moment a difference is explained by a category rather than by items, print the items; a category explanation reads as settled and cannot be falsified.
- **A matcher and a pathspec are different instruments on the same command shape.** `rev-list --objects <ref> -- path` and `rev-list --objects <ref> | grep path` look like the same query and returned 1,169 versus 859 on the same ref and the same tree. **Pin four things, not three: the ref, the instrument, the pattern, AND whether the last argument is a matcher or a pathspec.**
- **A state table being written while you read it makes every claim from it a timestamp — and a zero is the most perishable value in it.** Two agents read `deleted: 0` from the same live sync table within the hour; by the end of the evening it was **3**, because the vault performed a repair in between. **A zero that can move is not a finding, it is a reading.** Record the time with any count taken from a table a live process owns, and re-read before quoting it as evidence that something cannot happen — especially when the claim is "this vault has never produced X", because the act of measuring does not stop the writer.
- **A local client database is structurally incapable of measuring server-side accumulation — check the SCHEMA before proposing it as an instrument.** A sync state table held one row per path with a single uid and **zero history/version rows**, because the client keeps current state locally and asks the server for `history`/`restore` explicitly. **So "the table shows no version rows" is not evidence that versions do not accumulate; it is evidence that the table was never the instrument for that question.** Before calling a measurement impossible, confirm the tool COULD have shown the thing you are looking for.

- **A rate limiter's log records its own DECISION, not the downstream outcome — "saturated with entries landing" is evidence that slots were GRANTED, not that work succeeded.** A queue reported a write gate "at 20/20 with entries every +25s" as proof that pushes were flowing; reading the gate at source showed it appends its record and prints `granted` *before* the command it guards runs. **The gate guards the gate; the remote is the receipt.** When you need to prove a channel is live, read the far end (an authenticated API probe, an `ls-remote` tip) rather than the local coordinator's log — a coordinator with 20/20 entries and 268 lifetime defers proves only that it was busy.
- **A contract that exists as a habit will be re-asked as a defect.** A seat reported "cannot push" as a fault; the answer was that write access is deliberately centralised (one lock, one credential, one serialised gate — because parallel writers from one credential are what got the account flagged). **Unstated design reads as breakage.** When a capability is absent ON PURPOSE, write the contract where the affected seat will find it; otherwise every seat re-measures the absence and files it again.
- **Name the OWNER, not just the repo, when a permission reads false.** A queue item recorded "org repos read `push:false`" — but the repo lives under the **user** `GentechLabs` while the **org** is `Gentech-Labs`, two different accounts, and the org path 404s. **A permissions claim against the wrong owner is unfalsifiable and survives for weeks.** Check `api.github.com/user` vs `/orgs/<name>` before recording who owns what.

- **Never `.split()` a git author field — a two-word name becomes two people.** Counting distinct authors with `.split()` on `%an` produced **20 values from 17 real authors and invented an author that does not exist** (`Jordan` 105 + `Jones` 104 were halves of `Jordan Jones`, whose real count is 104). **A tokeniser asked to do a parser's job fabricates entities, and the fabrication looks like data.** Split on LINES for `--format=%an`; `--format='%an %cn'` and `git shortlog -sne` produce the same doubling by design.
- **A count is meaningless without the RULE, and the rule is often a sentence nobody wrote down.** The same 6,506 commits yield **20% "seat-named", 63% "prefix-shaped", 97% "any leading word"** depending on one line of matching logic. Three agents reported three different splits of the same history and **none of them was wrong** — they had drawn the line in different places and never stated where. **Publish the predicate with the number**, the same way a scan must report its window; the missing artefact here was not a script but a sentence.
- **Two predicates with nearly equal values will be confused forever unless both are named.** `folder:true` = 2,749, zero-byte rows = 2,750, zero-byte-and-no-extension = 2,506 — **a label was attached to the wrong predicate and survived review because the numbers are within 1 or 2 of each other.** When counts cluster within a few units, name each predicate explicitly at the point of use; near-equal values cannot be told apart by inspection.

- **A self-healing list only heals the part you generate; a SEED it copies verbatim is never re-evaluated.** An exclusion list is regenerated every 30 minutes — it walks the vault and adds junk paths — but its policy lines are **copied from a file that only ever gets appended to**, so an entry naming a folder that no longer exists is carried forever. **Two exclusion entries were proved dead, then proved gone, because the policy file was rewritten by hand in between.** When auditing a generated artifact, find the SEED and ask what could ever remove a line from it; a generator that only adds cannot heal its own inputs.
- **"Excludes zero FILES" is not "excludes nothing" — folders leak, files do not.** A directory was classified "empty" because the walk counted **files = 0**; it held **476 directories** and 101 immediate entries. **The exclusion does work for content and says nothing about structure**, which is the same distinction as the earlier acquittal: an acquittal is only as good as the unit it was computed in. **Count FILES and DIRECTORIES separately before calling anything empty or cleared.**
- **A count is only comparable if the pattern set that produced it is stated — "real events" is not a quantity.** Two agents measured the same log three ways and got 306, 343 and 406; a fourth value published earlier was 160 lines wider than **any** predicate its author could name. **The rule: publish the predicate beside the number, and print the tool's own check in its output** so the next reader inherits the definition instead of re-deriving it. **A bucket wider than every check you can state is not a scope, it is an artefact.**

- **Before publishing a threshold from a client's code, print the numeric token's CONTEXT — `5242880` and `52428800` differ by one digit and mean 5 MiB vs 50 MiB.** A cap was published as `5 * 1024 * 1024` and hardened into a shipped safety tool. Measured at source: the only token in that range is **52428800 (50 MiB, the "File exceeds 50MB upload limit" check)**; **a standalone `5242880` has ZERO occurrences — grep found the substring, not the constant.** The client's real per-file limit is **`perFileMax = 199*1024*1024`, SET BY THE SERVER at login**, so it is not a local constant at all. **Rules: (1) match the token with a digit-boundary regex, never a substring search; (2) if a threshold can be server-supplied, it is not knowable from the client source — report it as unknown rather than substituting a plausible number; (3) a threshold you cannot read becomes a PRE-FILTER, and the output must say so, not claim a pass.**
- **"Silent failure" is a claim about the LOG, so check the log before writing it in a docstring.** A tool's header asserted oversize files "are SILENTLY never uploaded"; the client's `logSkip()` **writes a line per path (deduped)**, so an oversize skip is logged, never silent. **Measured: 0 occurrences of the skip string in a 9,873-line `sync.log`** — the cap had never fired, which is exactly why nobody could have measured the claim from the log. **Say "unmeasured" rather than "silent": the absence of a log line is evidence the event never happened, not that it would go unlogged.**
- **A correction that lives in only one copy does not reach the reader who opens the other — and the artifact of record is the one that gets linked.** A broadcast went out to four seat inboxes; the delivered copies carried the correction block, the **vault note of record carried the bare pre-correction assertion and zero correction blocks**. A peer caught the drift and reported it **inverted** (naming the delivery stale). **When you correct a claim, sweep the artifact of record AND every delivered copy, and state each copy's read time** — a delivered message is read once, the vault note is read forever.
- **A cap that has never fired has never been measured — and a tool built to watch it inherits the myth.** A safety check was shipped around a threshold nobody could reproduce; a peer read the file at a stable path, quoted the constant, and the constant did not exist. **Before hardening a number into a control, re-derive it from source with a boundary-matched search; a control wired to an invented threshold fails open on real data while reporting a pass.**

- **A "only-here" count is a property of the COMPARISON SET, not of the objects — name both sides of the subtraction or the number is unreproducible even by its author.** A one-way-door figure went out as *"2,536 objects exist nowhere else"*: the number could not be re-derived under **any** of the 2,048 subsets of the refs on the host, its nearest achievable neighbours were 1,236 and 4,454, and it is now withdrawn. The same repository produces 868, 880, 1,236, 13,592 or 62,884 depending on which refs you subtract — **and the media count swings from 0 to 399 purely by choosing ONE ref (`main`) as the comparison, because every one of those 399 media objects is present in another ref.** **Publish the excluded-ref list beside the number, and when a figure is called a risk, name which of the two sides is the live set.**
- **When a number is called into question, re-derive it exhaustively before defending or abandoning it — the achievable set is often small enough to enumerate.** A challenged figure was checked by generating **all 2,048 subsets** of the comparison refs and recording each achievable total. **That converted "I cannot reproduce it" into "it is unreachable from any subset, and the nearest alternatives are X and Y"** — a far stronger result than a failed single retry, and it took one script. **A spread of candidate answers is also a finding: a figure sitting BETWEEN two nameable universes is a measurement of some unnamed set, not of the artifact.**
- **Before publishing a count from a repo, state it as a triple — the refs INCLUDED, the refs EXCLUDED, and the instrument — because a partial union of refs is a universe nobody can reconstruct.** Two agents independently produced the same error in opposite directions: one counted from a single ref and missed six live ones; the other counted from every ref a clone had. **The rule is not "count all the refs" (a clone's refs are not the repository's); it is NAME THE UNIVERSE.**
- **A destructive option can WIDEN the set a later destructive option takes — model the COMPOUND, not each option alone.** Neither retargeting a branch nor rewriting its history alone endangered two blobs, because both were reached through the ancestry of a shared ref **plus** six other branches. **But rewriting the branch severs exactly that ancestry link, leaving the blobs reachable only from the six branches — the same bucket a later prune takes.** **When filing a preservation decision, check whether the options INTERACT: "safe under (a) or (b)" is not the same claim as "safe under (a) then a prune".**

- **A test that greps for a function's NAME will match its `def` line, so `head -1` returns the definition no matter where the call is — or whether it exists.** A case named "the target is validated before use" computed `guardline` from `grep "guard(refspec, ref)" | head -1`, which matched `def guard(refspec, ref):` at the top of the file. **Measured with the call site DELETED ENTIRELY: the case still PASSED.** **Anchor a source-inspection test on the CALL (`problem = guard(...)`, or the assignment form) and exclude `def`, or the assertion is satisfied by a declaration that is never removed.** A test that cannot fail is worse than a missing test, because it is counted.
- **Ordering and reachability are different claims — a green suite can confirm the weaker one while missing the stronger.** A guard was correctly placed before the push and correctly asserted to be before it, while an earlier `return` (a graph query) still made it unreachable from the CLI: the refusal came back with the wrong reason. **Asserting `call_line < push_line` proves nothing about whether control ARRIVES; assert the call precedes EVERY other return that can fire first, and then invoke the firing case through the real entry point.** The proof that a control works is that reverting the code turns the new cases red — so keep the revert cheap enough to re-run.
- **A source-inspection test must run against a SUBJECT-OVERRIDABLE path, or the negative control requires an in-place edit of the live artifact.** A suite hardcoded its subject to the vault path, so proving the test could fail meant swapping the real safety tool in place and restoring it by hash. **Make the subject a parameter (env var / flag) and default it to production**; a control you must edit the subject to run is a control the next reader will skip.
- **When a fix is reported with a negative control, reproduce the control rather than the claim — and run it against the strongest form of the defect, not the one described.** Rebuilding the previous version's shape confirmed three cases went red; deleting the call outright found a FOURTH case that could not fail at all. **The described defect is the one the author already thought about; the strongest form is the one that tests the test.**

- **When a question needs an instrument you lack, look for the CODE PATH before inventing a measurement — the source often answers what the data cannot.** A peer could not tell whether excluded-path rows were **survivors** of a config change or rows the client was **still creating**, and named it unresolved rather than guessing. **The client's own filter answered it: `if (folder && path === r || path.startsWith(r + "/")) return false` — an excluded FOLDER is rejected on the creation path, so they cannot be new.** **Then one measurement confirmed it: 153 rows created after the last excluded-path row, and ZERO of them inside an excluded path.** **The table could not distinguish the two hypotheses; the source plus a rowid watermark could.**
- **A config change that filters the FUTURE leaves everything already pushed in place — check for a retroactive removal path before promising that re-indexing clears anything.** The client's `changeFilter()` collects rows the old filter rejected, re-tests them under the new list, and returns only those that **now pass** (the un-exclude direction). **Nothing in it removes a row that BECOMES excluded.** So an added exclusion stops future syncs and leaves stale records behind — **the records are inert, and a re-index clears them, but only because nothing is still writing them.**
- **A directory exclusion removes content and leaves STRUCTURE — and the residual grows with directory count, not file count.** Measured on one tree: **14,015 files on disk, ZERO file rows on the server (the exclusion works completely on content), while 628 of 978 directory nodes still had rows.** **So state the residual in rows and the payload in bytes; a structure-only residual carries no payload and stays stable as files accumulate.** Never report the row count and the payload as if they were the same quantity.
- **When two readers differ by a small count over a path list, DIFF THE LISTS — a one-row-per-path total closes by naming, not by re-counting.** An 18-row gap decomposed exactly: **agreement to the row on the two large terms, plus a 6-row set one reader's predicate captured and a 17-vs-15 difference in a folder that holds one row per path.** The disagreement was a predicate, not arithmetic — and the only way to show that is to publish both lists.

- **Two "sizes" in one table are usually two different things — measure the DELTA between them across every file before quoting either.** A folder was reported by two readers as 83.90 MB and 83.9 MiB and both were called the same number; they were — but a second, unnamed pair was underneath. **Measured across 3,363 files, `server_size − disk_size = +28` on 3,350 of them: a uniform per-file delta is ENCRYPTION OVERHEAD, so the server column is the CIPHERTEXT size and disk is the plaintext size.** **A constant that does not scale with content size is a header/tag, not padding** (here 28 B; composition 12-byte nonce + 16-byte tag is an INFERENCE — measurable delta, unmeasurable composition). **When a ledger charges for transfers, it charges for the encrypted bytes — quote that one.**

# Pitfalls — part 1 of 3

Part of the `develop-and-verify` ledger. **Index, part list and the census rule: `pitfalls.md`.**
Items were **MOVED WHOLE** from the single-file ledger on 2026-09-28 — never rewritten — so each carries its own
provenance line inside its own text. **Part 3 is the LIVE part; new lessons append there.**

- **Import paths when wrapping existing code** — Use `sys.path.insert()` or `Path.resolve().parent.parent` to import from sibling directories
- **CDN-clouded verification — static asset behind Cloudflare** — When deploying a static asset (HTML, JSON, image) through nginx to a domain proxied by Cloudflare, a successful `curl http://localhost/path` does NOT mean `https://domain/path` will serve the same content. Cloudflare Workers can intercept URL paths on the root domain even when wrangler.toml only routes `/api/*` and `/v1/*`. The Worker's catch-all handler (a `jsonResponse({ error: 'not_found' })` in the worker.ts `fetch()` fallthrough) returns 200 with API-style JSON for any unhandled path — which hides the error. Fix: (1) verify locally first, (2) verify externally with a content check, (3) if mismatched, check whether a Worker on the root domain is intercepting the path and remove the route from the Worker's wrangler.toml or add a passthrough in the Worker's fetch handler.
- **nginx `server_name` mismatch when testing via localhost** — `curl http://localhost/path` does NOT test the nginx server block for your domain. It hits the **default server block** (the first block that matches `listen 80 default_server`, or the alphabetically-first `sites-enabled` file). A 404 from `http://localhost/` is NOT evidence the site is down — it could mean the request matched a different server block entirely. Always use `curl -H "Host: yourdomain.net" http://localhost/path` to simulate the correct virtual host. Confirmed Jul 28, 2026: `curl http://localhost/frameforge.html` → 404 (wrong server block), `curl -H "Host: gentechlabs.net" http://localhost/frameforge.html` → 200 (correct).
- **Uvicorn module import path mismatch** — When running `uvicorn api.server:app`, Python resolves imports relative to the `api` package, NOT the project root. A `from cache import ScoreCache` in `api/server.py` fails because Python looks inside `api/` for a `cache` module, not at the project root. Fix: add `sys.path.insert(0, str(Path(__file__).resolve().parent))` at the top of `api/server.py` BEFORE the FastAPI imports. This makes sibling modules (`cache.py`, `payment.py`, `agent_identity.py`) importable whether the server is run as `uvicorn server:app` (from project root) or `uvicorn api.server:app` (from anywhere). Test this by running the server and hitting the health endpoint — if it starts but returns 404 on new endpoints, the import path is wrong.
- **Empty state file from tempfile** — `tempfile.mkstemp()` creates a 0-byte file. Guard with `if not content.strip(): return {}` before parsing
- **Writing code before tests** → harder to verify correctness
- **No plan saved to file** → subagents lose context, repeat work
- **Skipping audit** → security issues slip through
- **Phantom persistence** → "I saved the file" without verification. Always read-back after write
- **Overengineering** → 1000 lines when 100 would do. "Would a senior engineer say this is overcomplicated?"
- **Weak success criteria** → "make it work" is unverifiable. Transform to testable goals
- **Patch tool failure** — When patch fails repeatedly, switch to `write_file` to rewrite the entire file
- **Subagent timeout with partial output** — Subagents may timeout at 600s but have created all files. Verify with `find`, run tests, fix remaining issues manually
- **Re-read files after subagent build** — Subagents may have changed imports, function signatures, or branding
- **Subagent won't clean up stale files** — After a pivot or major refactor, manually remove old files
- **ES modules require a web server** — Games using `<script type="module">` won't work via `file://`. Serve via `python3 -m http.server 8080`
- **FastAPI/uvicorn port conflicts** — Port 8080 is commonly occupied. Use 8088 or scan first
- **FastAPI `request := Request` uses the class, not the instance** — `request := Request` in a route function assigns the `Request` class (a Starlette property object), not the injected request instance. FastAPI injects the request automatically when you add `request: Request` as a parameter. Fix: `async def get_price(request: Request, ...)` — never `request := Request` inside the function body
- **Python f-string backslash in expression** — `f"...{', '.join(f'{k} (${v["amount"]})' for ...)}"` fails because f-string expressions can't contain backslashes. Fix: extract the inner expression to a variable first: `tier_str = ", ".join(...)` then `f"...{tier_str}"`
- **`py_compile` passing is NOT the module importing** — A syntax check is blind to name resolution. A module compiles cleanly and still dies on import when a function is called at **module scope** but **defined further down the file** (Python runs top-to-bottom; a `def` below its first call is too late), or when a helper/global is referenced before it exists. A sweep reporting "N/N compile" has proven **nothing** about whether those files can RUN. Verify by importing, not compiling:
  ```python
  import importlib.util as u
  s = u.spec_from_file_location('m', path); m = u.module_from_spec(s)
  s.loader.exec_module(m)          # the real check
  ```
  Better still, run the tool's own `--help` or a dry-run. Caught live Sep 22 2026: a whole migration reported 86/86 files compiling while one could not be executed at all.
- **A "last resort" fallback that calls itself is infinite recursion, not a fallback** — `except Exception: return _helper()` where `_helper` is the function you are already inside recurses until the stack dies. The final branch must return a **literal**. A fallback path that has never been executed is not a fallback — test it by simulating the unavailable dependency (raise the ImportError) and asserting the literal comes back.
- **A caller in the deploy/sync manifest does not mean its CALLEE is** — When a wrapper script is enrolled for deployment but the script it *invokes* is not, the wrapper updates while the thing that actually runs stays stale — and the wrapper's own checks still pass. When enrolling a script, walk its **call graph** (what it `source`s, `bash`es, or `python`s) and enroll those too. Symptom: vault and deployed copies with **different line counts** — that is divergence, not formatting.
- **A single-RPC post-state read can print the PRE-action balances after a SUCCESSFUL action** — Re-reading balances on the same connection that just broadcast can show the old state, which reads exactly like a failed transaction. Never present that as fact. Read a **second, different provider** and print an explicit **delta** (`before -> after (+X)`), plus a hard warning when a tx reported SUCCESS but shows zero movement: that is a **lagging node, not a failed operation** — and explicitly say **do NOT re-send**, because re-sending doubles the action.
- **FastAPI module import side effects** — Extract business logic into standalone modules with no FastAPI dependencies
- **pytest-asyncio async fixture mode** — Add `asyncio_mode = "auto"` to `pyproject.toml` under `[tool.pytest.ini_options]`
- **SQLite `:memory:` path guard** — `os.path.dirname(":memory:")` returns `""`. Guard with `if dirname:` before `os.makedirs`
- **SQLite upsert pattern** — `UPDATE` does nothing if no row exists. Always `INSERT OR IGNORE` first
- **Python filenames with hyphens** — Can't be imported. Create underscore alias: `cp dry-powder-engine.py dry_powder_engine.py`
- **Bloomed node_modules block GitHub push** — Always `.gitignore` node_modules, build artifacts, and binary caches in the initial commit
- **`assert_close` defined after use in test files** — When writing inline test scripts (not pytest), define helper functions like `assert_close` BEFORE the test functions that call them. Python executes top-to-bottom, so a function used at module scope must be defined earlier in the file. Fix: move all helper definitions to the top of the file, right after imports.
- **CLI subprocess tests need fresh state per invocation** — Each `subprocess.run([sys.executable, "module.py", ...])` spawns a fresh Python process with a new in-memory state. If test A creates data and test B reads it via subprocess, test B won't see test A's data. Fix: either (a) create + read in a single `-c` script, or (b) use the module's Python API directly instead of subprocess. Proven on P2P Causes: flyer test failed because `cause-1` didn't exist in the subprocess's fresh engine.
- **Sequential build for medium independent tasks** — When the queue has 4-6 medium-sized independent tasks, sequential processing (one at a time, same session) is often faster than parallel subagents. No coordination overhead, no import-path confusion, no stale-file cleanup. Each task takes 2-5 minutes end-to-end. Use parallel subagents only when tasks are large enough (3+ files each) that wall-clock time savings outweigh setup overhead.
- **Phantom PRs — verify PR existence after creation** — `gh pr create` can exit 0 without the PR actually existing on GitHub. Forks can be silently deleted between sessions. Always verify with `gh pr view <number> -R <owner/repo> --json state` after creation, and re-verify all PRs at the start of every session. A PR that exists only in your tracking is a phantom PR — it wastes reviewer time and damages reputation when maintainers see stale references.
- **Circular imports when splitting modules** — When extracting shared helpers from a FastAPI app module (e.g. `gateway.py`) into a new module (`tab_or_exact.py`), the new module may import from the original, creating a circular dependency. Fix: extract the shared functions (config, helpers, models) into a third module (`helpers.py`) that has zero FastAPI dependencies. Both the original and the new module import from the helper, never from each other. Pattern: `gateway.py` and `tab_or_exact.py` both import from `helpers.py`; neither imports from the other.
- **C library compilation on import (liboqs-python pattern)** — Some Python packages (e.g. `liboqs-python`) trigger a full C library build from source on first `import`. This takes 5+ minutes on a VPS and will timeout any normal 10-30s terminal command. The build does eventually succeed, so the fix is to start the import in a background process (`terminal(background=True, notify_on_complete=True)`) first, then build the framework code while it compiles. After it finishes, the oqs module is available normally. Detection: if `import oqs` takes > 2 seconds or spawns a liboqs installation dialog, it's compiling — don't kill it, start it in the background and keep working.
- **Package directory names with hyphens are unimportable** — A package directory named `agentic-treasury` (with hyphen) cannot be imported by Python (`ModuleNotFoundError: No module named 'agentic_treasury'`). Python packages require underscores or camelCase. Fix: use `quantum_treasury` (underscore), never hyphens. If you already created the dir with a hyphen, `mv agentic-treasury quantum_treasury` and update all imports. Tests running via `pytest` from a parent directory will fail until this rename is done.
- **liboqs/oqs key lifecycle — in-memory only** — The `oqs.Signature` object stores signing keys internally in C memory and does NOT expose a `set_secret_key()` or `export_secret_key()` method. Once the context manager exits or the object is garbage collected, the key is gone. Pattern for signing: keep a live `oqs.Signature` instance on the signer object (`self._signer_ref`), call `generate_keypair()` once, then `sign(message)` on the same instance. For verification, create a fresh `oqs.Signature(alg)` and call `verify(message, sig, pub_key)` — verifiers don't need the secret. Persistent SPHINCS+ key storage requires wrapping oqs in a daemon that keeps a live reference.
- **A test written OUTSIDE the harness's fixture scope passes for the wrong reason** — The negative control ("strip the fix, the test must fail") is the only thing that catches this. A check that depends on a patched global (monkeypatched `_bases()`, a temp dir, an injected fake) written *outside* the patch context runs against the REAL system, finds nothing, and returns the expected value without exercising the code at all. It is green, it is unfalsifiable, and it will be cited as proof the fix works. Symptom: strip the guard and the check still passes. Fix: keep every such check inside the patch scope and comment WHY the scope is load-bearing so nobody "tidies" it out. Caught live Sep 28 2026 in `test-handoff-watcher-closure.py`: two new checks (B7, B6c) were written below the `finally` that restored `_bases`, both passed with the guard removed, and both were proving nothing.
- **A "pre-fix" control anchored on `HEAD` drifts as soon as anyone commits** — Comparing against `HEAD` to prove a fix changed behaviour only works if `HEAD` still predates the fix; once a peer lands a commit touching the same file, `HEAD` already contains it and the control silently reads clean. Anchor on the **commit that actually precedes the fix** (`<fix-sha>^`), or the test's own baseline revision — never the moving branch tip. Same failure as measuring a file while another seat is mid-write. Caught live Sep 28 2026: the `HEAD` control read 18/19 (looked fine) while the true pre-fix `a841e35a0^` read 16/19 with the expected checks red.
- **A STALE ARTIFACT DOES NOT STAY INERT — a frozen copy keeps being LOADABLE and keeps ANSWERING.** A clone frozen at an old revision is not a harmless duplicate: if it sits at a GENERIC name, it is the thing most likely to be loaded, and its stale claims are read first. Measured 2026-09-28: a 1158-line root `SKILL.md` frozen since Sep 22, byte-identical on 4 seats, sat at the category root and its model table recommended three models that share ZERO entries with the two core-backed routing skills — while the live runtime was on a different model entirely. It even deferred to the correct skill in its own prose; the stale table still led. **The question is not 'is this copy correct?' but 'is this copy REACHED?'** — and a name that is more generic is more reachable, so the least-maintained copy is often the first-read one. Corollary of the uniformity pitfall: a clone at a generic path is not just invisible evidence, it is visible misinformation.
- **A REACH CLAIM IS ONLY AS WIDE AS THE SET OF CARRIERS YOU CHECKED — measure the CONTENT's reach, not ONE carrier's.** A single carrier that fails to propagate tells you NOTHING about whether the content spread by another route. Measured 2026-09-28: a skill with no core copy reached 1 of 4 seats, and that was reported as the TOPIC's reach ("the guidance reaches 2 of 4") when a second, core-backed carrier was already delivering the same content to 4 of 4. The error is not the measurement, it is the SCOPE of the conclusion: one carrier's status is a fact about that carrier, not about the content. **Before claiming a topic reached N seats, enumerate the carriers and check each.** And when you receive such a number, re-derive it — inheriting someone else's scope error propagates the error one layer further, which is what happened here: a peer's 2-of-4 went into a doc and had to be corrected to 4-of-4. Sibling of the uniformity pitfall: agreement is not reach, and a failed carrier is not absence.
- **A UNIFORMITY CHECK CANNOT FAIL — a frozen clone passes it by construction.** "Every seat has this file, and all copies are identical" reads as a strong propagation claim and is worth nothing: a clone produces uniformity automatically, so agreement is evidence of a copy, not of a live carrier. Measured 2026-09-28: three seat copies of a skill were byte-identical AND nanosecond-identical in mtime (44c469ba6f1f, .629295858) while the fourth had been hand-edited — one clone, not four agreeing files, and nothing propagated any of them. The only signal that separates a live carrier from a frozen snapshot is whether the file has MOVED since the snapshot, and a snapshot cannot see that because it has no source to compare against. **Check the SOURCE, not the agreement** — same class as a check that can never go red, and as a manifest that certifies drift as uniformity. Corollary: a seat-only edit is SAFE BUT INERT — no sync can overwrite a file it never collects, so it cannot be destroyed and cannot travel.
- **A non-following fetch returns a clean-looking NOTHING — check the status code AND the byte count** — `curl -s` without `-L` on a redirecting URL returns the redirect status with an EMPTY body: **HTTP 308, 0 bytes**. Nothing errors, nothing warns, and a search for your target text simply finds nothing — which reads as "the page no longer says that" when the page was never fetched. A redirect is a real status code with zero content, so the failure is silent in exactly the direction that makes you doubt live data. Rule: fetch with `-L`, print `%{http_code}` AND `%{size_download}`, and treat `0 bytes` as a failed fetch rather than as an absence. Caught live Sep 28 2026: a non-following fetch reported 308/0 on a page that returns 200/17,048 with `-L`, and the empty result briefly looked like evidence the content had been removed. Same class as a parse reporting on a document it never located.
- **A DIGEST written into prose has no clue it has aged — pin to a COMPARISON, not a value** — This is the third form of the moving-anchor class, beside a `HEAD` control and a shared-clone branch tip. An `md5`/`sha` recorded in a *document* describes the instant it was written: the moment anything touches the file it is stale, and unlike a commit it carries **no marker of having moved** — it reads exactly like a current fact. A commit hash in a report is scoped by its own history (you can ask whether it is an ancestor); a bare digest is scoped by nothing. A manifest is the safe form because its checker RECOMPUTES the digest and COMPARES rather than trusting the recorded value; prose has no such check, which is fine as narrative and dangerous as evidence. Caught live Sep 28 2026: a handoff verified a skill as `c04815c91e`; within the hour the skill moved to `eba67ace07` when a sibling lesson landed, and the prose pin silently became false while looking authoritative. Rule: in prose, cite WHAT YOU COMPARED AT READ TIME ('md5sum of both paths, diff clean'), never the digest itself; if a literal value must appear, state the date it was true.
- **A parse of an artifact is not the artifact — quote the tool's own output** — Piping a tool (or a document) through your own reader and then believing the reader is how a wrong number acquires the authority of a measurement. Two instances in one session, both reporting confidently on something they had not correctly located: `git show … | grep -n` matched a docstring that *quotes* the old code and was read as the live function; a hand-rolled gate counter printed `0/20` in the same second the gate itself printed `20/20`. Fix: take the number from the thing that owns it — the tool's own printed line, the program's own exit status — and treat your parse as a hint, never a receipt. Ask explicitly: *is what I parsed the thing I meant?* (Sibling of "count the artifact with the tool that owns it", which owns the declarative-structure case.)
- **Never accept a blame you have not measured, and never assign one you have not measured** — When a peer's failure report implies you shared the bug, "I must have had the same bug" is an assumption dressed as humility: a self-criticism that is also a false claim is still a false claim. Check whether the mechanism could have produced YOUR error before accepting it, and state what you found either way. Its mirror: do not hand a peer an implied fault without the measurement that supports it. Caught live Sep 28 2026: an instrument lesson (hand-rolled parsers mis-handle a structure's own comments) implied a peer shared the parser bug; they checked and did not — the delimiter occurred exactly once, so their capture was sound. Their real error was narrower and different: publishing a FILTERED count as if it described the whole artifact.
- **Count the artifact with the tool that owns it, not with a parser of it** — A hand-rolled reader of a declarative structure (a shell array, a config block, a generated list) will mis-handle the structure's own comment syntax and report a number it invented. The owning tool cannot be wrong about its own contents: `source` the block and read `${#ARRAY[@]}`. Caught live Sep 28 2026: two successive Python passes over a `SCRIPTS=(...)` array returned 4311 and 3535 tokens because the array's comments contain parentheses and apostrophes, while bash reported 246 — and a third pass returned 244 because the extension allowlist I wrote listed `.md` and omitted `.js`. Symptom: publishing a count that changes when you re-run your own instrument. Cross-check the number with a second instrument before it leaves your hands; a count you cannot reproduce is not a measurement.
- **A verifier that checks only what it knows how to check reports a clean fleet while an unrecorded copy drifts** — A deployer/verifier with a hardcoded file list answers "is what I know about uniform?" and never "is there anything I do not know about?". The gap is invisible precisely because it is outside the instrument: every check passes, and the thing that fell behind was never in the list. Caught live Sep 28 2026: a fleet deployer named ONE file while exactly one seat copy of a *test* existed elsewhere, unlisted, and had drifted six checks behind — every run reported the fleet uniform. Fix: make the expected set explicit and recorded (a manifest), verify the RECORD against reality as well as reality against the source, and prefer a mode that reports drift without writing (cron-safe). Symptom to watch for: multiple propagation mechanisms and no single place answering "what goes where".
- **A guard gated for a reason needs a check on the REASON, not just on the gate** — If a condition exists to protect a behaviour, a test that only proves the gate FIRES leaves that behaviour undefended: the same guard hoisted or removed still passes every check. A guard and its justification are two propositions and each needs its own falsifier. Caught live Sep 28 2026: a date-only guard is gated to filed dirs *because* a daily roundup legitimately pairs with the same-named note in the reverse LIVE lane. The suite proved the filed-dir block (B7) and nothing proved the pairing it protects — so HOISTING that guard (the exact mutation that had already un-resolved a real daily note) left the suite **green at 19/19**. It was caught by regression-sweeping the vault, not by the test. Fix: add the opposite-direction check (B7b: the pairing MUST still work), then the hoist goes red. Symptom: a mutation you know is harmful, applied to the code, with every check still green.
- **A zero-delta is only evidence if your instrument CAN show non-zero** — Before accepting "the fix changes 0 verdicts" as proof of safety, prove the same measurement returns non-zero when the fix is absent. A sweep pointed at the wrong function (or the wrong scope) reports a clean zero and looks like a passing safety check. Caught live Sep 28 2026 verifying a peer's guard-scope claim: `is_resolved()` over 517 notes reported **0 changed** when the guard was hoisted — because the guard lives in `_has_return_note()`, a different function entirely. The same mutation measured on the right instrument (`_has_return_note` over 63 outbound handoffs) found **exactly 1** daily roundup un-resolved, matching the peer's figure. Rule: name the function under test, then confirm the negative arm moves the number. Same failure mode as a test written outside its fixture scope — green for the wrong reason.
- **A hardcoded identifier is the bug whichever identifier it is — resolve it, and if resolution fails, say so** — `vault_push_drain.py` hardcoded `REMOTE_BRANCH = "origin/main"` plus `git fetch origin` and `git push origin main`. When the vault's remote was renamed `origin` -> `vault`, the fetch failed, the `rev-list` count failed, `pending` went to `-1`, and the script exited **0** every 20 minutes printing `cannot read the unpushed count` — a green light on a dead leg for ~2.5h while the fleet's memory had no off-box copy. Prefer the fleet's documented name, fall back to the conventional one, and never let an unresolvable name degrade into the silent/clean branch. `git remote` is one command; a rename is not a reason for a monitor to stop monitoring.
- **Distinguish a permanent failure from a retryable wait — reporting one in the other's vocabulary disables the alarm** — the same script's failure path labelled EVERY non-deferral `"the gate keeps deferring"`. The gate is the *benign* reason a push does not land (wait and retry works); a **fork** is a different mechanism with a different remedy (a merge; retrying never lands it). A permanent condition reported as a clock is retried forever and never escalates. Classify the failure, name the remedy, and make the speak-rate different: a fork should say *"this needs a merge, not a wait"* promptly, a deferral should stay quiet and retry.
- **A count without its universe is not reproducible — state the scope beside the number, or the next reader measures a different one and neither of you is wrong** — I filed *"903 media objects reachable from `vault/main` vs **0** from local main"*. The `0` was true for **one path** (`music/vanito/`) and false for the object graph, where local main still carries 1117 media objects (1025 under `Gentech/`, outside the purge's scope). A peer measured 1114/1527 and our totals agreed to within the extension set — **the scope was the whole disagreement, and it read as a contradiction about the facts.** Same class, three times in one day: 995/1001 (hidden files), 135/131 (a seat root counted as a skill), 42/42 (two definitions of "subdir" that happen to collide, so the error leaves no trace). Write the universe with the number — `music/vanito/` objects, ALL media objects, media files in the TREE, media objects in HISTORY — because "media count" and "purged" are each at least two different measurements.
- **A permanent condition must be read from the STATE, never from the outcome of an action that can be gated, skipped or deferred.** I inferred "the branch has FORKED" from the push REJECTION — then the write gate deferred the push, git was never invoked, no rejection was observed, and a permanently-diverged branch was reported as `DEFERRED` ("retry next tick") forever. **The fix I had just shipped for gate-vs-flag reproduced the class one level down, in the same script, in the same hour.** Ask the graph (`git merge-base --is-ancestor <remote> HEAD`) — it cannot be deferred. Two costs, and I had counted one: the mislabel AND a doomed attempt that still spent a scarce gate slot (the counter now reads 20->20 across a run). **When a condition is permanent, prove it from state; when you infer it from a failure, any earlier step that can short-circuit hides it.**
- **Size a measurement window to the ARTIFACT, not to the population — and a bare token is not a pattern.** Two bounds, both measured the hard way in one day. **Too narrow loses the artifact:** `*.log` cannot match the rotated `agent.log.1`, so after one rotation the same instrument reads 0 for events that are unchanged — and a DECAYING count reports *improvement* on *worse* data. **Too wide actively loses:** widening a window from 64 files to 537 added ZERO events and one real hazard, because the extra files hold *copies* of the artifact — a census run from inside an agent writes its own output to `cache/terminal-output/out-*.log`, so a profile-wide glob would GROW ITS OWN EVIDENCE and inflate on every run. **And a bare token matches things that are not the artifact:** `grep -c '429'` also matches the millisecond field `HH:MM:SS,429`, and the inflation scales with TRAFFIC, so a busy seat reads worse than a quiet one for reasons unrelated to the metric — the instrument's error correlates with the thing it measures. Match a phrase or an anchored pattern, and print the loose count BESIDE the anchored one so the inflated number cannot be quoted apart from its correction. **Count the artifact with the tool that owns it** is the *what*; this is the *where*.
- **A negative from a bounded search is a fact about the SEARCH, not about the world — never write it into a canonical doc as a permanent condition.** I filed *"the exclusion list is not on disk and cannot be checked"* into the fleet's canonical transport protocol. It was a 63-entry array in a JSON file at a named path. I concluded it did not exist from **one CLI line** (`No sync configuration found`) plus **`find -maxdepth 2`** — the file sits at **depth 4**. Both were bounded instruments, and I reported their empty result as a property of the disk. **State the bound with the negative** ("no `*.json` at depth 2") or do not state it, and **re-check before generalising a transient** — `not found` is a fact about the command, the path, the depth and the moment. The cost here was three wrong headlines inside one canonical document, discovered by a peer opening a 596-byte file neither of us had read.
- **A delta across two lines is ADDITIVE, not invariant: `delta(union) = SUM of delta(class)` — and "invariance" is what additivity LOOKS LIKE when the classes you add carry zero delta.** Measured at a pinned, immutable commit pair: img 304 + vid 77 + aud 32 = 413 EXACT. Adding a class present on both sides moves nothing (it contributes 0); removing a class removes exactly its own delta. **A reader told to expect an invariant hunts for a constant that is really a SUM.** Always state the extension classes WITH the delta — the same pair of commits gives 413 on one class definition and 389 on another, **24 apart, with no residue and no disagreement.** Also: **when two careful people get DIFFERENT totals for the same artifact, check whether the DIFFERENCE agrees** — if it does, they are measuring the same thing and the gap is in the units.
- **A total summed over a SUPERSET can neither acquit nor convict a SUBSET.** A "the rewrite may not have completed anywhere" conclusion was drawn from 1,114 remaining media objects — which sit in paths the purge never targeted (1,022 of them under one unrelated folder). **Match the scope of the measurement to the scope of the claim.** This is the same error as a path-scoped zero written as a whole-graph number, **facing the other way**: one agent stated a whole-graph number from a scope, the other a scope conclusion from a whole-graph total. Ask *"what is this a total OVER?"* before using it to decide anything about a part.
- **A named guard that nothing reads is decoration — confirm the mechanism DOING the protecting is the one the name points at.** A `NEVER_TOUCH = "main"` constant sat in a fast-forward-only updater and was referenced **zero times**; the actual guarantee was the hardcoded refspec `HEAD:refs/heads/backup`. Nothing was broken, and that is the danger: **every named guard read as satisfied while the real protection lived somewhere with no name.** Before trusting a guard, **grep its USES, not just its definition**, and check that the line someone would change in a hurry is the line the guard reads.
- **A freshness step inside a tool protects the TOOL, not the hand that calls it.** A script that fetches the remote ref before counting always reports a fresh delta — but anyone counting by hand from a stale local ref gets a number that is wrong **and plausible**, and the tool's freshness does nothing for them. **The manual run is therefore the dangerous path, not the automatic one.** State the instrument and its refresh with any count reported from outside the tool. **Corollary, measured the same night:** a stale ref does not yield a *fixed* wrong number — it yields whatever the difference was **when that ref was last updated**, so a remembered figure like `53` is a moment, not a property, and it keeps growing while you argue about it.

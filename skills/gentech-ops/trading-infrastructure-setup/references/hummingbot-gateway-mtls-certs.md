# Hummingbot Gateway mTLS Cert Fix (SEC-048)

The Hummingbot Gateway (v2.x) runs **secured mode with mTLS** — it will NOT start without
a full cert set. If the certs dir is empty, the gateway **crash-loops** with:

```
Error: ENOENT: no such file or directory, open './certs/server_key.pem'
    at getHttpsOptions (/home/gateway/dist/https.js:13:27)
[ELIFECYCLE] Command failed with exit code 7.
```

## Root cause
`dist/https.js` reads `server_key.pem`, `server_cert.pem`, `ca_cert.pem` from
`server.certificatePath` (default `./certs/`) and decrypts the key with the passphrase from
`GATEWAY_PASSPHRASE` env (or `--passphrase` arg). No certs → crash. The certs are normally
generated by the Hummingbot CLI (`gateway generate-certs`), NOT inside the gateway image —
so a bare `gateway/start` on a fresh box fails.

## The fix (openssl, no Hummingbot CLI needed)

The passphrase is `GATEWAY_PASSPHRASE` from the gateway container env (e.g. `gentech_config_2026`).
Generate the full mTLS set into the host certs dir (the gateway's certs are a **read-only
bind mount** from the host, so edit the host files):

```bash
cd /hummingbot-api/bots/gateway-files/certs   # host path mounted into gateway container
PASS=gentech_config_2026

# CA
openssl genrsa -aes256 -passout pass:$PASS -out ca_key.pem 2048
openssl req -x509 -new -nodes -key ca_key.pem -sha256 -days 3650 -passin pass:$PASS \
  -subj "/CN=GenTech Gateway CA" -out ca_cert.pem

# Server key + CSR — CRITICAL: SAN must cover the hostname the API connects to
openssl genrsa -aes256 -passout pass:$PASS -out server_key.pem 2048
openssl req -new -key server_key.pem -passin pass:$PASS -subj "/CN=gateway" \
  -addext "subjectAltName=DNS:gateway,DNS:localhost,IP:127.0.0.1" -out server.csr
openssl x509 -req -in server.csr -CA ca_cert.pem -CAkey ca_key.pem -CAcreateserial \
  -out server_cert.pem -days 3650 -sha256 -passin pass:$PASS \
  -extfile <(echo "subjectAltName=DNS:gateway,DNS:localhost,IP:127.0.0.1")

# Client key + CSR + sign (the API presents this to the gateway)
openssl genrsa -aes256 -passout pass:$PASS -out client_key.pem 2048
openssl req -new -key client_key.pem -passin pass:$PASS -subj "/CN=localhost" -out client.csr
openssl x509 -req -in client.csr -CA ca_cert.pem -CAkey ca_key.pem -CAcreateserial \
  -out client_cert.pem -days 3650 -sha256 -passin pass:$PASS
```

## The hostname-mismatch pitfall (the one that bites)
The API connects to the gateway as `https://gateway:15888` (from `GATEWAY_URL`). If the
server cert is `CN=localhost` with no SAN for `gateway`, the API fails with:

```
[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: Hostname mismatch,
certificate is not valid for 'gateway'.
```

**Always add `DNS:gateway` to the server cert SAN.** Verify with:
```bash
openssl x509 -in server_cert.pem -noout -ext subjectAltName
```

## Syncing certs to the API container (TWO places)
The API process reads client certs from **two** locations — both must have the NEW certs
(they are separate filesystems; the API container's own dir is NOT the host mount):

1. **API cwd certs dir** — `/hummingbot-api/bots/gateway-files/certs/` (inside the container).
   `build_client_ssl_context()` reads from `gateway_certs_dir()` = `os.getcwd()/bots/gateway-files/certs`.
2. **`root_path()/certs`** — hummingbot's in-process `GatewayHttpClient` reads only from
   `root_path()/certs` (e.g. `/opt/conda/envs/hummingbot-api/lib/python3.12/site-packages/certs`).

Copy the new `ca_cert.pem`, `client_cert.pem`, `client_key.pem` into BOTH, then restart the
API container so the cached SSL context rebuilds:
```bash
for f in ca_cert.pem client_cert.pem client_key.pem; do
  docker cp /hummingbot-api/bots/gateway-files/certs/$f hummingbot-api:/hummingbot-api/bots/gateway-files/certs/$f
  docker cp /hummingbot-api/bots/gateway-files/certs/$f hummingbot-api:/opt/conda/envs/hummingbot-api/lib/python3.12/site-packages/certs/$f
done
docker restart hummingbot-api
```

## Verify end-to-end
The API's `/gateway/chains` and `/gateway/connectors` are the real test. A raw urllib/curl
test WITHOUT a client cert will always fail with `TLSV13_ALERT_CERTIFICATE_REQUIRED` — that's
expected (mTLS). Test WITH the client cert from inside the API container:
```bash
docker exec hummingbot-api python3 -c "
import asyncio, sys, aiohttp
sys.path.insert(0,'/hummingbot-api')
from utils.gateway_certs import build_client_ssl_context
async def main():
    ctx = build_client_ssl_context('gentech_config_2026')
    async with aiohttp.ClientSession(connector=aiohttp.TCPConnector(ssl=ctx)) as s:
        async with s.get('https://gateway:15888/', timeout=5) as r:
            print(r.status, await r.text())   # expect 200 {"status":"ok"}
asyncio.run(main())"
```

Then via the API: `curl -u USER:PASS http://localhost:8002/gateway/chains` should return the
chain list (ethereum + solana), and `/gateway/connectors` should list `meteora` (clmm),
`jupiter` (router), `raydium`, `uniswap` — the connectors the Consigliere needs for the
Builders Cup.

## Gateway lifecycle via the API
- `POST /gateway/start` with body `{}` (GatewayConfig defaults: image `hummingbot/gateway:latest`,
  port 15888). Returns a container_id.
- `POST /gateway/stop` — stops the gateway container.
- `GET /gateway/status` — `{"running": true/false, ...}`.
- The gateway binds to `0.0.0.0:15888` (warns it's reachable from the network) — fund-moving
  routes require the API token (`GATEWAY_API_KEY` / conf/api-key). Prefer keeping it on the
  tailnet/VPN.

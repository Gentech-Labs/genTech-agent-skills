# Measurement time in generated messages

## The rule

Any automated message that reports a **derived, time-sensitive claim** — age, staleness, "open
X hours", "last seen", "N jobs failing", "Y checks passed" — must include **when it was measured**
in the message body itself. Do not rely on chat timestamps, cron logs, or the receiver's
willingness to look up the generator's state.

Derived claims are computed when the generator runs. They are read when the message arrives, or
later when the message is quoted, forwarded, replayed by a bot, or surfaced in a digest. Those
two moments can be minutes or hours apart. A message that doesn't say which moment its numbers
come from forces the reader to assume "now" — and every stale delivery becomes a false finding.

## Why "channel metadata" is not enough

- Chat timestamps are often stripped in quotes/forwards.
- Digest jobs aggregate multiple messages and may reorder them.
- Cron logs are not visible to the message recipient in the same UI.
- A message can be replayed by another agent or a test harness with a different clock.

Only the **body** survives all of those transformations unchanged.

## Minimal safe form

```
⚠️ AS OF {UTC HH:MMZ} — if you have acted since this was generated, this <message type> is STALE:
re-check before acting, and do not treat it as a live finding.
```

Place it adjacent to the derived claim, not buried in a footer, so it cannot be separated from
the number it qualifies.

## Examples where this applies

| Generator | Derived claim | Stale-reading cost |
|-----------|--------------|--------------------|
| handoff watcher | `open 10h, no return` | re-verify an already-closed handoff |
| health monitor | `N jobs failing` | chase a transient error that has already auto-healed |
| repo audit | `X drift hits` | spend a round trip disproving a stale hash |
| data sync report | `Y files stale` | re-run a sync that has already finished |
| build digest | `Z items blocked` | re-open a conversation that was unblocked |

## Anti-patterns to avoid

- **"Generated at HH:MM" in a footer only.** Footers get dropped when the message is quoted.
- **"Age" computed from a filename/date prefix.** That age is frozen at generation; it keeps
  saying the same thing even as real wall-clock time advances, which makes stale reads look
  current.
- **No timestamp + a number that sounds live.** This is the dangerous default. If the number
  can change after generation, the message must say when it was true.

## Practical check

Before declaring a generated message fixed, ask:

1. Does the body contain a measurement timestamp?
2. Is there an explicit stale-warning tied to that timestamp?
3. If the message is quoted without its original context, does the claim still look qualified?

If any answer is no, the message is not safe for async delivery.

## The absence of the stamp is itself a measurement (2026-09-28)

An hour after the `AS OF` stamp shipped, **the same nudge arrived a second time** — and it was
triaged in seconds *because* the stamp was missing from it. The delivered copy carried no
`AS OF` line, so it could only have been generated by pre-fix code and delivered afterwards;
the cron confirmed the last sweep ran ~6.5h before the delivery. **The nudge was truthful
when written and false when read.**

The durable rule this gives you:

> **A fix that makes a recurrence SELF-EVIDENT is worth more than one that prevents it.** You
> cannot predict which stale message will be replayed, so the property you actually need is
> that an old message is *recognisable as old on sight*. Adding the stamp did not stop the
> replay; it made the replay cost nothing to dismiss.

Corollary: when you add a measurement stamp, **expect old un-stamped copies to keep
circulating** for the length of whatever queue replays them. That is not the fix failing —
it is the fix working, and the reader must be told to treat a *missing* stamp as the stale
signal. State this in the handoff, because the next reader will otherwise think the fix
didn't deploy.

## A generated message must NAME ITS OWN AUTHOR from the data (2026-09-28)

The same nudge **hardcoded the author in its header** while interpolating the sender in its
body:

```python
f"HQ → {peer}: handoff waiting on you.\n\n"          # hardcoded
f"  {sender} → {receiver} · open {int(hours)}h, no return\n"   # interpolated
```

A nudge about a `pixel → …` note therefore read *"HQ → gentech-treasury"* on line 1 and
*"pixel → gentech-treasury"* on line 3 — **one message naming two different authors.** It
never fired only because every nudge in the fleet's history happened to come from `gentech`.

Rule: **any field a message asserts about itself — author, seat, source lane — comes from the
data, never a literal.** The tell is a message where *some* occurrences of a value are
interpolated and others are typed; the typed one is the bug, and it hides because it is
correct for the common case.

When you fix it, **fall back to the raw value, never a guess**:

```python
SENDER_DISPLAY = {"gentech": "HQ", "gentech-treasury": "Treasury", ...}
def sender_display(lane):
    return SENDER_DISPLAY.get((lane or "").strip(), lane)   # unknown -> its own name
```

A wrong label is worse than an unfamiliar one, because a reader interprets it as a
*correction* rather than as missing data.

## A count from a LIVE tree is a reading, not a constant (2026-09-28)

Measuring a shared, actively-written tree (the vault, a live branch, a log) produces numbers that
are **true at the measurement instant and false later**. Real instance: reporting the divergence
between two vault lines gave *"259 unique local commits"* — re-measured twenty minutes later, on
the same tree, the same command read **264**. Neither number was wrong; the tree moved.

The failure is not in the measurement, it is in **shipping a bare number**. A reader cannot tell
whether 259 is stale or current, and will act on it either way.

Rules:

1. **Every count from a live tree carries its instant:** *"264 unique commits (as of 18:05Z)"* —
   the same `AS OF` discipline required of any generated message. A count without one is
   unfalsifiable: nobody can check it without re-deriving when it was taken.
2. **Prefer the durable artifact over the perishable count.** A branch, a commit sha, or a file
   path stays true; a commit count or a file total does not. When you preserve work, *name the
   ref*, not the tally — the ref is checkable forever, the tally is checkable only today.
3. **If you are correcting your own number, name the drift in the correction.** Publishing
   "259 → 264" teaches the reader that the measurement is live; silently updating to 264 hides
   exactly the property that makes the number risky.

The tell that you are about to get this wrong: writing a number about something you are *also*
changing, or about a tree other seats are writing to right now. That is when the instant matters
most and is most likely to be omitted.

## The container question: what am I summing over, and can it hold the same event twice?

Every inflated count found in the rate-limit census was **the same event counted in two containers**:

| container | the artifact | the fix |
|---|---|---|
| log **destination** | the same line written to `agent.log` AND `errors.log` | `set()` over the line |
| **seat** | two seats log the same second | `set()` over the union, not the sum |
| **field inside one line** | `timestamp[:23]` keeps `,960` — milliseconds wearing the name "seconds" | validate the length (19), don't truncate to a number that looks right |

**Rule: before summing, ask whether the container can hold the same event twice.** A per-seat total, a per-file
total, and a per-field extraction are all answers to "what am I summing over" — and all three were wrong by the
same mechanism. **A `set()` is the whole fix in every case; the difficulty is noticing the container is one.**

**Corollary — a quantity is only as good as the name you gave it.** The field was *called* seconds, so when it
read lower than the line count it looked like the tighter estimator; it was structurally looser, because
truncating to a millisecond barely dedupes a burst. **A name is a claim. Validate that the value satisfies it.**

## The wrong-scope family: two modes, two different questions

Every inflated figure found in the rate-limit census was **the same quantity in the wrong scope**, and there are
**two modes**, caught by **two different questions**. Ask both — they are not the same test.

**MODE 1 — a container counted twice.** The same event in `agent.log` AND `errors.log`; the same second on two
seats; the same instant under two truncations. **The question: can the container hold the same event twice?**
Fixed by `set()`.

**MODE 2 — a comparison across scopes.** The denominator never covered the numerator: all-classes seconds divided
by one class's refs, so a "ratio" compared two different universes. **Nothing was counted twice; the count was
correct and the ratio was meaningless.** **The question: does the denominator COVER the numerator?**

| | Mode 1 | Mode 2 |
|---|---|---|
| ask it of | a **total** | a **ratio** |
| the assumption that fails | numerator and denominator share a universe | (none needed — it inspects the scopes) |
| symptom | the number is too big | the number is **unfalsifiable**, and moves with an undocumented class list |

**A ratio built from two scopes is not a tight estimate — it is not an estimate at all.** If the class list is not
printed beside it, the reader cannot even tell it is wrong. **Either print per-class ratios, or keep the pooled
figure with an explicit `MIXED UNIVERSE — DO NOT QUOTE` warning — never delete it, because a deleted number leaves
the next reader to rediscover why it was wrong.**
